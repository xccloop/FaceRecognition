# 技术选型：每个选择背后都有一个 Bug

> 简历上写"使用 C++/ncnn 替代 Python 推理"只是一行字。
> 但真正经历过 Python 推理跑出 5 FPS、两个进程抢摄像头、MJPEG 靠写文件传输导致画面卡死之后，
> 你就不会再把它写成"技术选型"了——你会把它写成**踩坑记录**。
>
> 这篇文章还原了项目中每个关键技术决策对应的真实错误。
> 没有一个是"我觉得这个更好"——全是"不这么做就过不去"。

---

## 1. 为什么推理用 C++ 而不是 Python？

### 直接原因：5 FPS → 30 FPS

最早的树莓派推理管线是用 Python + ONNX Runtime 写的。结果跑出来 **5 FPS**（Bug 52）。

瓶颈分析：
- 每帧做全分辨率检测（640×480），无效计算太多
- Python 三重循环手动解码 ncnn 输出，而不是向量化
- 每帧都提取特征（哪怕同一张脸连续出现 30 次）
- onnxruntime 每帧往 stderr 打 warning

修了一轮后提升到 20-30 FPS，但代价是代码里塞满了跳帧逻辑、特征缓存、IOU 跟踪这些本该由引擎层处理的东西。Python 代码越来越像 C++ 的拙劣模仿。

### 更深层的原因：两个进程抢摄像头（Bug 34）

Python 架构天然分了两个进程——推理进程和 MJPEG 推流进程。两个进程都想独占 `/dev/video0`，第二个打开时报 `Device busy`。

C++ 单进程天然解决了这个问题：摄像头只打开一次，MJPEG 推流直接拿内存中的帧，不需要文件中转。

### 附带的教训：MJPEG 写文件传输导致画面卡死（Bug 40）

Python 版本的 MJPEG 推流是推理进程把 JPEG 写入文件，推流进程从文件读取。如果推理进程因为任何原因停止写入（比如在处理一帧耗时长的图片），推流进程会反复发送同一帧，浏览器表现就是"画面卡死"。

C++ 版本用 `std::mutex` 共享内存中的最新帧，推流线程直接在内存中取——零文件 I/O，不需要文件系统介入。

**一句话总结**：不是 "C++ 比 Python 快"，而是单进程 + 内存直传 + 无 Python 解释器开销的架构，天然解决了三个互相独立的 bug。

## 2. 为什么自定义 COBS+CRC8 帧协议？

### 初版协议的灾难：伪帧头（Bug 7）

最早的协议很简单：

```
0xAA + CMD + DIR + LEN_H + LEN_L + DATA + XOR + 0x55
```

问题很快出现：二进制数据中可能出现 `0xAA` 字节。比如识别结果的人名是"郭"（GBK 编码 `0xB9 0xF9`），但如果传的是照片数据或者某种巧合值，数据区出现了 `0xAA`，接收端就会误判为新帧开始，导致上一个帧被截断、下一个帧从半截开始解析。

初版修复是引入 `0xBB` 转义（类似 SLIP 协议）：

```
0xAA → 0xBB 0x55
0x55 → 0xBB 0xAA
0xBB → 0xBB 0x44
```

但转义引入了新的问题——帧长度不可预测（数据中的 `0xAA/0x55/0xBB` 越多，帧越长），且转义逻辑散落在编解码两端，维护成本高。

### 为什么最终选了 COBS

COBS（Consistent Overhead Byte Stuffing）用一种更优雅的方式解决了同样的问题：

- **开销可控**：最坏情况每 254 字节多 1 字节（约 0.4%），不像转义方案可能膨胀 100%
- **规则简单**：编码和解码各约 20 行代码
- **0x00 天然帧定界**：COBS 保证编码后不含 0x00，所以用 0x00 做帧分隔符不会产生歧义——不需要像 0xAA/0x55 方案那样担心"数据里刚好有这个字节"

### 为什么加了 CRC8（Bug 9）

初版用 XOR（异或）做校验。但 XOR 只能检测奇数个比特错误，且发送端和接收端 XOR 覆盖的字段范围如果不一致（漏了某个字节），校验就形同虚设。

CRC8 的查表实现（256 字节预计算表）计算效率不比 XOR 差多少，但检错能力远超 XOR：
- 任何单比特错误
- 任何奇数个比特错误
- 任何 ≤8 位的突发错误
- 约 99.6% 的更长的突发错误

**一句话总结**：不是因为"协议设计看起来厉害"，而是 XOR 校验漏了 Bug 9 那种假阳性、0xAA 伪帧头导致 Bug 7 的丢帧——不升级协议框架，可靠性根本过不去。

## 3. 为什么 STM32 用 FreeRTOS 而不是裸机？

### 直接原因：裸机轮询处理不了多件事

STM32 需要同时做：接收 UART 帧、解析协议、执行命令（开门/亮灯/显示）、检测心跳超时、喂看门狗。裸机下写成状态机不是不行，但很容易出现"某个步骤耗时长了，其他事情全被阻塞"。

### ISR 中调用错误 API 导致 HardFault（Bug 1）

最早的尝试是直接在 UART 接收中断里处理帧解析。在 ISR 里调了 `xQueueSend()` 而不是 `xQueueSendFromISR()`，程序直接 HardFault。

这是个典型的"不知道为什么但这样做就崩了"的问题。调试之后才理解：FreeRTOS 的 ISR 版本 API 会通过 `pxHigherPriorityTaskWoken` 参数告知调度器是否需要切换任务——这是 FreeRTOS 任务调度模型的核心机制。

### 任务栈溢出导致随机卡死（Bug 3）

帧解析函数里定义了一个 256 字节的局部数组，任务栈只有 `configMINIMAL_STACK_SIZE`（约 128 字 = 512 字节）。栈溢出后程序表现是"随机卡死"——溢出覆盖了相邻内存，可能恰好没覆盖关键数据，所以有时正常有时崩。这种 bug 在裸机下更难定位。

### 静态分配 vs 动态分配（Bug 4）

FreeRTOS 默认用动态分配（`pvPortMalloc`），但嵌入式系统长期运行下有堆碎片风险。切到静态分配后，需要自己提供 idle 任务和 timer 任务的 TCB 和栈空间——漏掉就会报 `undefined reference`，编译都过不去。

**一句话总结**：不是为了"用 RTOS"而用 RTOS，而是裸机下处理多任务并发 + 错误恢复的成本，远高于学 FreeRTOS 的成本。

## 4. 为什么用 DMA 而不是中断逐字节接收？

### ORE：一个字节毁掉一帧（Bug 6）

最早的 UART 接收方案是中断逐字节——每收到一个字节触发 RXNE 中断，ISR 读 DR 寄存器。115200 波特率下，一字节约 87μs，ISR 的处理时间如果超过这个间隔，下一个字节就会触发 ORE（Overrun Error）。

**ORE 的后果是灾难性的**：ORE 标志置位后，RXNE 不再置位——中断不再触发。看起来像是"串口突然沉默了"，实际上是接收逻辑永久性死锁。

修复方式是在 ISR 中检查 ORE 标志并清除：

```c
if (USART_GetFlagStatus(USART1, USART_FLAG_ORE)) {
    USART_ReceiveData(USART1);  // 读 DR 清除 ORE
}
```

但即便如此，ORE 期间丢失的字节已经不可挽回——至少丢了一整帧。

### DMA 环形模式彻底解决 ORE

DMA 环形模式让硬件自动把收到的字节搬进环形缓冲区，CPU 只需要在 IDLE 中断（一帧接收完成后）介入：

- 不存在"CPU 来不及读了"的问题，DMA 负责搬运
- ORE 即使发生（极其罕见），`on_error()` 重启 DMA 即可，不会有永久性死锁
- ring buffer 的 `head` 指针由 DMA ISR 在 HT/TC 中断中推进，`tail` 指针由任务在消费时推进——**并发安全，不用锁**

### CNDTR 差值法（Bug 17 的诊断过程）

调试时发现 DMA 配好了但没收数据，通过打印 `cndtr`（DMA 剩余计数寄存器）发现值一直是 1024（满缓冲），说明 DMA 一个字节都没收。最终定位是发送端波特率不匹配。

CNDTR 这个寄存器后来成了 RX 接收逻辑的核心：通过两次读取 CNDTR 的差值（考虑环形回绕）计算新收到的字节数。这个算法在 `uart_dma.c:rx_update()` 中一共 8 行：

```c
if (curr <= prev)  delta = prev - curr;         // 正常情况
else               delta = prev + (capacity - curr);  // 环形绕回
rb_advance_head(&h->rx_rb, delta);
```

**一句话总结**：不是"DMA 比中断高级"，而是中断逐字节的 ORE 死锁（Bug 6）决定了 115200 波特率下必须用 DMA。DMA 之后，CNDTR 差值法和环形缓冲成了自然而然的设计延伸。

## 5. 为什么用 ncnn 而不是 ONNX Runtime？

### ncnn 的动态 Shape 层噩梦（Bug 48）

最初尝试在树莓派上直接用 ONNX Runtime，但树莓派 ARM 版的 onnxruntime 编译和维护都很痛苦。换了 ncnn 之后，新的问题来了：

ONNX 模型中的 `Shape`、`Gather`、`ExpandDims` 三个算子——ncnn 不支持。onnx2ncnn 转换工具直接报 `"layer Shape not exists or registered"`。

尝试写自定义层注册绕过，写了三版：
1. 第一版 pass-through（直接 clone 输入）→ 推理不报错但返回全零结果
2. 第二版改进了 Shape 和 Gather → 仍然 segfault
3. 第三版删掉了 ExpandDims 的自定义（因为 `ExpandDims` 是 ncnn 内置层，我的注册覆盖了正确实现）→ 还是不行

**最终结论**：onnx2ncnn 转换工具对非标准 ONNX 图的兼容性有限。直接用 pnnx（PyTorch → ncnn）是对的，但 ONNX 中转这条路对于复杂模型走不通。

### 关键点偏移灾难（Bug 54 + Bug 55）

同一张图、同一个模型，**C++ ncnn 和 Python ONNX 推理结果的余弦相似度只有 0.14**——接近随机。这意味着两端的识别结果完全不同。

追了三个根因：

**根因 1 — 预处理不一致**：C++ 用 min-side 缩放 + 大量灰边填充，Python 用 max-side 缩放 + 零填充。灰边在 FPN 特征金字塔层产生非零激活，污染了检测头。

**根因 2 — Interp 层硬编码尺寸**：`det_500m.param` 中两个插值层的输出尺寸写死了 `output_height=30 output_width=40`，只适配 640×480 输入。换了输入尺寸就会维度错乱。修复是手工改 param 文件为动态 Interp（`height_scale=2.0 width_scale=2.0`）。

**根因 3（最隐蔽）— ncnn Reshape 后通道排列变化**：ncnn 的 `Reshape(0=10)` 把 20 通道合并为 10 通道，每个通道的空间维度翻倍。C++ 解码代码假设通道存储模式是 `[anchor0_kp0_x, anchor0_kp0_y]`，但 ncnn 实际合并后变成了 `[anchor0_kp0_x, anchor0_kp1_x]`。**所有关键点坐标按错误的通道索引读取，5 个关键点全被分配到错误的 x/y 值**。

修复是引入 `sub`（anchor 子类型编号）和 `pos`（空间位置）两个索引变量，正确区分锚点编号和空间维度的对应关系。

**一句话总结**：不是故意选 ncnn 来"做优化"，是模型转换过程中的 Shape 层不兼容（Bug 48）、预处理对齐（Bug 54）、通道排列（Bug 55）三个阶段**逼着你把推理管线吃透**。这些 bug 修完之后，你对检测模型的内部数据流比直接调 onnxruntime.run() 清楚得多。

## 6. 为什么用 systemd 而不是 nohup？

### SSH 断开进程就没了（Bug 38）

最早在树莓派上直接 `./facerec run &` 启动，SSH 一断进程就被 SIGHUP 杀掉了。`nohup` 能解决这个问题，但又不会自动重启——进程 crash 了就真没了。

### 重启风暴 65 次（Bug 39）

加了 systemd 的 `Restart=on-failure` 之后，一个未处理的摄像头空帧异常导致进程退出 → systemd 自动重启 → 又异常退出 → 循环 65 次。

`journalctl -u face-recognition` 看到 Restart counter 飙到 65 的那一刻就知道：**不能只靠外部守护，程序内部必须处理所有可能的异常**。后来在主循环加了 try/catch，空帧改为自动重连摄像头。

**一句话总结**：systemd 不是因为"标准化部署"，而是 Bug 38（SSH 断开丢进程）和 Bug 39（重启风暴）让你学会怎么写出不会被 systemd 频繁重启的程序。

## 7. 为什么 MJPEG 推流用 raw socket 而不是框架？

### 两个进程抢摄像头（Bug 34，重复但视角不同）

如果用 Flask 或 nginx-rtmp 推流，意味着又一个进程要打开 `/dev/video0`。树莓派上两个进程同时访问摄像头 → `Device busy`。

### TCP Nagle 导致画面卡顿（Bug 41）

最早的 MJPEG 实现没有设 `TCP_NODELAY`，TCP 默认的 Nagle 算法会等待缓冲区填满（或收到 ACK）再发送——这对实时视频流是灾难性的。每一帧 JPEG 约 4-7KB，Nagle 算法可能把它拆成多个 MSS（最大分段大小）再等 ACK，导致浏览器端收到帧的时间不可预测，画面一顿一顿。

```cpp
int on = 1;
setsockopt(client, IPPROTO_TCP, TCP_NODELAY, &on, sizeof(on));
```

一行代码，帧率从不可用到流畅。

### 为什么不用第三方流媒体方案

rtmp/webrtc/hls 确实更"专业"，但：
- 要引入额外依赖（编译、部署、维护）
- 对嵌入式场景过重
- MJPEG 虽然画质和带宽都不占优，但**在局域网内够用**且**实现简单**

**一句话总结**：选 raw socket 不是要炫技，而是它刚好解决了"不抢摄像头 + 不需要额外进程 + 一行代码关掉 Nagle"这三个约束。

## 8. 为什么同步用持久化队列 + 指数退避？

### 为什么不是一次性同步

如果注册时调用一次 HTTP POST，失败了就提示"同步失败，请稍后重试"——用户体验差，而且需要人工干预。

### 为什么不是固定间隔重试

如果 Pi 刚好在重启（需要 30 秒），每 5 秒重试一次会在 Pi 恢复前浪费 6 次请求。更糟的是如果有多个用户同时同步失败，固定间隔会让它们"共振"——多个请求同时涌向一个还在恢复的服务。

### 指数退避 2/5/10 的设计

```
第 1 次失败 → 等 2s 重试    （可能是临时网络抖动）
第 2 次失败 → 等 5s 重试    （比抖动严重一点）
第 3 次失败 → 等 10s 重试   （可能是 Pi 在重启）
3 次全部失败 → 标记 failed  （不无限重试）
```

### 为什么持久化到 SQLite 而不是内存

SyncTask 放在内存队列里的话，Windows 后台进程重启（比如更新、崩溃）就丢了。SQLite 表保证进程重启后任务还在。

### 为什么注册前去重

如果两次注册同一个用户（比如手滑点了两次），直接 POST 注册会导致 Pi 端覆盖原有特征文件，增加无意义的同步开销。先去 `GET /api/features?name=xxx` 查一下 Pi 上是否已有同名用户。

**一句话总结**：持久化队列和指数退避不是因为"要做消息队列系统"，而是几十次手动"重试同步"之后你自然会想：能不能自动做这个事？能不能进程重启了还记得？能不能不要同时轰炸一个服务？

## 9. 为什么即使有以上所有措施，还是加了 IWDG？

### 软件保证不了 100% 不出 Bug

FreeRTOS 可能有死锁、DMA 环形缓冲可能有指针错乱、ncnn 推理可能 segfault。IWDG 是独立的硬件模块——使用独立的 LSI 时钟（~40kHz），不依赖系统时钟——即使系统时钟完全挂掉，看门狗照样倒计时。

### 配置阶段就踩了坑

**Bug 11**：IWDG 初始化后，FreeRTOS 调度器启动前的初始化代码跑太久（SPI Flash 初始化字库），IWDG 已经超时复位了——表现为系统 2 秒一次无限重启。修复是在 `vTaskStartScheduler()` 前额外喂一次狗。

**Bug 12**：LSI 时钟没使能就去配 IWDG → HardFault。修复是显式 `RCC_LSICmd(ENABLE)` 并等待就绪标志。

### 喂狗位置的学问

喂狗只放在 `vUartRxTask()` 循环末尾——整个系统只有这一个喂狗点：

```c
for (;;) {
    // ... 收数据、解析、分发 ...
    IWDG_ReloadCounter();  // ← 唯一喂狗点
}
```

如果这个任务卡死了——死锁、死循环、永久阻塞——狗不喂，4 秒后系统复位。如果在这个任务里某个步骤耗时长但不至于卡死，狗会被喂到，系统继续跑。

**一句话总结**：IWDG 不是因为"要做高可靠性系统"，而是在经历了系统的间歇性死机后，你需要一个你自己都无法阻止的兜底机制。

## 结尾

本文记录了 9 个关键选型背后的 50+ 个真实 Bug。这些选择的核心逻辑可以归纳为：

| 选什么 | 不是"这个更好" | 而是在解决 |
|--------|---------------|-----------|
| C++ 替代 Python | 性能 | 5FPS + 双进程抢摄像头 + MJPEG画面卡死 |
| COBS+CRC8 替代 XOR+转义 | 协议设计 | 伪帧头 + 状态机漂移 + XOR假阳性 |
| FreeRTOS 替代裸机 | RTOS | ISR HardFault + 栈溢出随机卡死 + 静态分配编译失败 |
| DMA 替代中断逐字节 | 高级外设 | ORE 永久死锁 + 数据丢失 |
| ncnn 替代 ONNX Runtime | 模型引擎 | Shape层不兼容 + 预处理差异 + 通道排列错乱 |
| systemd 替代 nohup | 服务管理 | SSH断连丢进程 + 65次重启风暴 |
| Raw Socket MJPEG 替代框架 | 流媒体 | 设备占用冲突 + TCP Nagle卡顿 |
| 持久化队列+退避 替代同步 | 系统工程 | 重试风暴 + 进程重启丢任务 |

问 "你用了什么技术" 是面试题。理解"**为什么要用这个技术**"才是你自己的答案。
