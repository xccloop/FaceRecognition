# Phone 端 — 理想架构设计

> 微信小程序人脸采集入口的架构分析与最佳实践方案

---

## 一、项目定位

Phone 端是 FaceRecognition 整体系统的人脸注册入口。它只有一个使命：

```
                       ┌──────────────────┐
                       │   微信小程序        │
                       │   拍照 + 填姓名    │
                       │   上传照片         │
                       └────────┬─────────┘
                                │ POST /api/register
                                │ (multipart/form-data)
                                ▼
            ┌───────────────────────────────────┐
            │       Windows 后台 (FastAPI)       │
            │   接收照片 → 存储 → 写数据库       │
            └───────────────┬───────────────────┘
                            │ 照片 + 姓名
                            ▼
            ┌───────────────────────────────────┐
            │          SQLite 数据库             │
            │   persons 表: id, name, photo_path │
            └───────────────────────────────────┘
```

## 二、系统总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                       FaceRecognition                         │
│                                                              │
│  ┌─────────┐    ┌─────────────┐    ┌──────────────────────┐  │
│  │  Phone  │    │   Windows   │    │        Linux         │  │
│  │  (入口)  │───▶│   (后台)     │───▶│    (边缘推理)         │  │
│  │ 拍照上传 │    │  管理+存储   │    │   NCNN 人脸识别       │  │
│  └─────────┘    └──────┬──────┘    └──────────────────────┘  │
│                        │                                     │
│                        ▼                                     │
│               ┌────────────────┐                             │
│               │    STM32       │                             │
│               │   (执行层)      │                             │
│               │   继电器/门禁   │                             │
│               └────────────────┘                             │
└──────────────────────────────────────────────────────────────┘
```

数据流向：
1. **Phone → Windows**: 用户拍照 + 姓名上传，windows 后台存入本地文件系统 + SQLite
2. **Windows → Linux**: 管理员触发人脸训练/更新，推送新照片到树莓派
3. **Linux → STM32**: 识别结果通过串口指令控制继电器（开门）
4. **Web 管理台**: 管理员在 Windows 的 Web 页面查看/管理所有人员

Phone 端只参与第 1 步，不涉及其它端。

## 四、技术选型详解

| 层 | 选型 | 理由 |
|----|------|------|
| **平台** | 微信小程序 | 用户无需安装 App，扫码即用；微信生态覆盖广 |
| **框架** | 原生开发 | 功能极简（单页 + 拍照 + 上传），不需要 uni-app / Taro 等跨端框架的额外复杂度 |
| **语言** | JavaScript (ES6+) + WXML + WXSS | 小程序原生支持，无编译成本 |
| **状态管理** | Page.data + app.globalData | 单页面，不需要 Vuex/Redux/MobX |
| **网络** | wx.uploadFile (multipart) | 图片文件直接用 multipart/form-data 上传，服务端无需额外 Base64 解码 |
| **存储** | wx.StorageSync | 仅存储服务器 IP 配置，读写频率极低，同步 API 即可 |
| **样式** | 原生 WXSS (rpx) | 750rpx = 屏幕宽度，自动适配所有机型 |

### 为什么不用 Base64 上传？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Base64 (wx.request)** | 请求体可自定义 | 编码后体积膨胀 ~33%，手机端内存峰值高 |
| **multipart (wx.uploadFile)** ✅ | 原生文件流，内存友好 | formData 字段限制 |
| **云开发存储** | 无需自建服务器 | 依赖微信云，与现有 Windows 后台架构不兼容 |

选择 multipart/form-data，与 Windows 后台 FastAPI 的 `UploadFile` 原生对接。

## 五、通信协议

### 5.1 注册接口

```
POST /api/register
Content-Type: multipart/form-data

Form Fields:
  photo:  <JPEG/PNG binary>    # 照片文件
  name:   "张三"                # 姓名

Response (200):
{
  "code": 0,                   // 0=成功, 1=失败
  "name": "张三",
  "message": ""                // 失败时含原因
}

Response (4xx/5xx):
{
  "code": 1,
  "message": "照片文件过大"
}
```

### 5.2 配置接口（预留）

```
GET /api/config
Response: { "version": "0.1.0", "maxPhotoSize": 5242880 }

POST /api/heartbeat
Response: { "status": "ok", "timestamp": 1716249600 }
```

### 5.3 网络拓扑

```
手机 (WiFi) ─── 局域网 (192.168.1.x/24) ─── Windows 后台
                    │
                    ├── 开发阶段：关闭域名校验
                    └── 上线阶段：配置 HTTPS + 合法域名
```

## 六、安全与隐私

### 6.1 当前阶段（内网 + 开发期）

| 措施 | 状态 |
|------|------|
| 服务器 IP 白名单 | 仅局域网可访问 |

## 八、状态机设计

注册页面有 4 个状态，通过 `data.photoPath`、`data.name`、`data.result` 组合控制：

```
                      ┌──────────┐
         启动         │  空表单   │
    ───────────────▶  │  photo="" │
                      │  name=""  │
                      │  result=null │
                      └─────┬────┘
                            │ 选照片
                            ▼
                      ┌──────────┐
                      │  有照片   │
                      │  photo=✓ │
                      │  name="" │
                      └─────┬────┘
                            │ 输入姓名
                            ▼
                      ┌──────────┐
                      │  可提交   │  ← 提交按钮解除 disabled
                      │  photo=✓ │
                      │  name=✓  │
                      └─────┬────┘
                            │ 点击提交
                            ▼
                      ┌──────────┐
                ┌─────│  提交中   │
                │     │  submitting=true │
                │     └─────┬────┘
                │           │ 服务器响应
                │     ┌─────┴─────┐
                │     ▼           ▼
                │ ┌────────┐  ┌────────┐
                │ │  成功   │  │  失败   │
                │ │ result= │  │ result= │
                │ │ success │  │ error   │
                │ └────┬───┘  └────┬────┘
                │      │ 继续注册   │ 重新拍摄/修改
                │      ▼           │
                │ ┌──────────┐    │
                └─│  重置     │◀───┘
                  │ photo=""  │
                  │ name=""   │
                  │ result=null│
                  └──────────┘
```

## 九、可扩展性规划

### 短期（v0.1 → v0.2）

- [ ] **服务器 IP 配置页**：独立 settings 页面，不硬编码 IP
- [ ] **批量注册模式**：连续拍照无需反复点击"继续注册"
- [ ] **照片质量控制**：上传前检查文件大小，超过阈值自动压缩

### 中期（v0.2 → v0.5）

- [ ] **人员列表查看**：手机端查看已注册人员（只读）
- [ ] **人脸检测前置**：利用小程序新版 API 在本地做简单人脸检测（确保照片含人脸）
- [ ] **离线队列**：网络断开时缓存待上传照片，恢复后自动重试

### 长期（v1.0+）

- [ ] **多语言支持**：i18n 国际化
- [ ] **照片水印**：日期 + 操作人水印
- [ ] **扫码登录**：管理员手机扫码直接进入 Windows 管理后台
- [ ] **语音录入姓名**：支持语音转文字填写姓名（辅助无障碍）

## 十、设计原则总结

| 原则 | 体现 |
|------|------|
| **单一职责** | 一个页面只做一件事：拍人脸 + 填姓名 + 上传 |
| **最小化依赖** | 不使用任何第三方库，仅微信原生 API |
| **防御式编程** | 所有网络请求有成功/失败分支，失败有友好提示 |
| **渐进增强** | 预留配置接口和扩展点，但不过度设计 |
| **移动端适配** | 全 rpx 单位，大按钮（≥80rpx），适合手指操作 |
